# 사용자 정의 VD 처리 요구사항

## 연속 가상디바이스 모드 추가 (2026-10-13)

물리 센서 등록은 선택 가능한 입력을 추가하며 가상디바이스를 자동 생성하지 않는다. 사용자가 입력과 계산식을 등록할 때 가상디바이스 하나가 생긴다. 하나의 센서를 여러 가상디바이스에서 재사용할 수 있다. 하나의 가상디바이스 안에 평균·최댓값·경보를 등록하면 가상디바이스 1개, 독립 출력 행 3개가 된다. 각 계산을 따로 등록하면 가상디바이스 3개가 된다. 입력·출력은 각각 최대 16개이다.

물리 측정 항목의 Device·DeviceStatus와 웹 행은 계속 분리한다. 연속 계산 결과는 가상디바이스의 출력 행·상태·이력이며 별도 파생 CRD를 생성하지 않는다. 입력 프로토콜과 계산은 분리한다. MQTT·Modbus TCP·OPC UA·Serial JSON·Sense HAT·HTTP JSON을 기존 Mapper에서 수집하며, 새 센서는 메타데이터 목록에 자동 표시하되 기존 입력 바인딩은 사용자가 명시적으로 수정할 때만 변경한다.

새 CONTINUOUS_EKUIPER v3 모드는 SERVICE와 개별 VD Pod를 요구하지 않는다. 일반 AMD64 워커 CG004의 `ekuiper` 네임스페이스에 설치된 eKuiper 2.4.2와 agent를 공유한다. 출력별 소유 규칙을 생성하고 제한된 산술·비교·논리식, scalar·AVG·MIN·MAX·임계값·필터를 제공한다. 기존 BATCH·FFT·AI·supervisor 경로는 유지하며 v1 연속 VD 간 연결은 지원하지 않는다.

기본 1초의 정렬된 tick에서 모든 필수 입력의 UID·실제 적용 설정·원래 관측 시각·세션 순서를 확인한다. 입력 누락·만료·설정 변경·연결 재수립 시 세대와 창을 초기화한다. 유효한 연속 tick의 창은 1–1024개이며, 사용자가 임의 SQL·sink·plugin을 제출할 수 없다. Mapper의 물리 읽기와 DMI 보고 횟수는 늘리지 않는다.

결과 전체는 별도 PostgreSQL에 기본 7일(1–30일) 저장하며 그래프 집계는 조회에서만 수행한다. 이력 장애 때 최신 결과는 계속 제공하고 누락 구간을 표시한다. 복구 뒤 과거 입력·결과를 재생하거나 소급 저장하지 않는다. CG002의 초기 400Gi PVC는 실제 저장 경로의 여유 공간 480Gi 이상을 사전 확인해야 한다. 500개 측정 항목·200개 활성 VD·500개 규칙 및 보수적인 저장 예산을 적용한다.

운영 활성화 전 실제 17개 측정 항목, 각 프로토콜 simulator, 기존 BATCH 회귀, 규모·저장 부하, 실제 24시간 연속 수용 검증이 필요하다. 기준은 p95 결과 전달 2초 이하, 정상 입력 손실·중복 없음, 제한된 메모리·큐이다. 확인하지 않은 결과를 통과로 기록하지 않는다. 기능 기본값은 비활성이다. 아래 요구사항과 이전 증거의 SERVICE/FFT/VD 연결은 기존 BATCH 모드에 해당한다.

## 기존 BATCH 모드

사용자가 물리 센서와 측정 항목을 선택해 VD를 만들고, 필터·이동평균·RMS·FFT·임계값을 순서대로 조합하며 파라미터를 설정한다.
공통 Processing Engine을 재사용하고 VD Profile 설정을 실제 Runtime에서 실행한다.
처리 결과를 다른 VD 또는 AI Workflow 입력으로 연결한다.
Dashboard에서 생성·수정·실행·상태·결과를 조회한다.

기존 KubeEdge Mapper, DeviceModel/Device CRD, VD Profile v2, Spring Boot, Runner와 Dashboard를 재사용한다.
센서마다 별도 프로그램이나 Pod를 만들지 않고 Mapper의 수집·scale/offset을 그대로 사용한다.
기존 구현과 호환성을 유지하며 기능별 테스트·수정과 회귀 검증을 수행한다.
마지막에는 실제 센서 → Mapper → VD 처리 → Workflow → Result를 검증한다.
실제 Kubernetes 검증이 불가능하면 미검증으로 기록한다. 운영 배포·실데이터 삭제는 별도 승인 전 수행하지 않는다.
