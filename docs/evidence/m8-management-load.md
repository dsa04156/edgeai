# M8 — 장치 관리 HTTP 부하 측정

2026-10-04 KST. M8 일부 측정이며 전체 단계·실장비·합의 성능 수용 완료 판정이 아니다.
[ADR0057](../adr/0057-device-management-load.md)과 [실행 방법](../load-testing.md)을 따른다.

## 실제 전체 규모 측정

`20261003T234836Z-e9dbbb5f`의 `test-load.sh --measure-only`가 exit0/MEASURED다.
전용 PostgreSQL DB와 별도 loopback API에서 장치를 누적100→300→1,000개 등록했다.
단계마다60초 동안 장치당10초 주기로 관측을 보내고 관측10개당 상세 조회1개를 추가했다.
아래 p95는 예정 발송 시각부터 응답까지로 대기·발송 지연을 포함한다.

| 장치 | 요청 수 | 제시 RPS | 완료 RPS | p95(ms) | p99(ms) | API CPU(core equivalent) | API 최고 RSS(MiB) |
|---|---:|---:|---:|---:|---:|---:|---:|
| 100 | 660 | 11 | 11.00 | 65.54 | 80.65 | 0.57 | 421.3 |
| 300 | 1,980 | 33 | 32.99 | 53.28 | 56.17 | 1.56 | 440.2 |
| 1,000 | 6,600 | 110 | 109.93 | 54.64 | 57.61 | 5.15 | 462.2 |

총9,240개 요청의 오류·누락은0이다. 페이지 조회의 장치 집합, 최신 session/sequence,
DB 관측 수710/2,740/9,540과 본문 속성이 일치했다. 단계별10/30/100개 장치에 동일 관측·boot
재전송, 새 세션, 이전 세션409를 확인했다. 각 단계 DB deadlock은0이며, 이 예상 거절에 따른
rollback은 요청 오류 수로 해석하지 않는다. 시험 종료 후 소유 API 중지·전용 DB 제거를 확인했다.

환경은 Linux x86_64·논리 CPU24개·호스트 메모리134,757,564,416bytes,
PostgreSQL16.15·API JVM 최대 heap512MiB·Hikari pool5·worker32/대기 상한64다.
API JAR SHA-256은 `3f9bfc03329367fdc594d7fa765b79dcee7a66274849fe8bd3617635581fc8ac`다.
도구가 별도 CPU quota를 설정하지 않으며 상위 실행 환경의 제한은 수집하지 않았다.
호스트와 PostgreSQL instance를 공유한다. CPU 값은 API 프로세스의 표본 구간
사용량이며 DB 또는 부하 생성기 CPU를 포함하지 않는다. 단일 실행 결과로 최대 수용 용량이나
원격 네트워크/클러스터 확장 성능을 주장하지 않는다. 원시 `report.json`을 실행 증거에 보존했다.

## 측정 도구와 판정 검증

- `20261003T235714Z-b52563e4`: 단위3개 PASS. 대기 지연과 요청 시간을 구분하고,
  느린 서버에 제시 부하를 낮추지 않으며, 잘못된 세션을 반환한 HTTP201을 실패로 분류한다.
- `20261003T235714Z-8cb1074e`: 실제 API/DB 네 가지 판정 회귀 PASS. 각각10대/2초에서
  요청22개·관측31개·자원 정리를 확인했다. 측정 전용은 exit0/MEASURED,
  예산 미정은 exit2/PENDING_ACCEPTANCE, 극소 예산 초과는 exit1/FAIL,
  넉넉한 예산의 소규모 시험은 exit2/PARTIAL_SCALE다. 이 두 시험 예산은 합의 성능 기준이 아니다.
- 같은 판정 회귀를 GitHub Actions scaffold에 연결했다. 새 변경의 CI 결과는 후속 확인한다.

첫 시도 `20261003T234543Z-9bdba054`는100대의660개 측정 요청 성공 뒤,
정합성 조회에 사용한 오래된 유휴 HTTP 연결이 닫혀 실패했다. 이미 보낸 요청을 재시도하는 대신
발송 전에5초 이상 유휴 연결을 교체하도록 수정했다. 위 전체 규모 재실행으로 후속 조회와
모든 단계의 정합성 검사가 통과함을 확인했다. 실패 실행도 부분 report와 정리 결과를 보존했다.

## 남은 범위

후속 별도1,000대/30초 진단에서 정합성·정리를 통과했고 JFR profile25초를 수집했다.
실행 표본11,551개 중11,459개(99.2%)가 BCrypt 계산 stack에 있었다. 같은 HTTP Basic 자격의
반복 검증이 이 구간의 CPU 병목이다. 원시 JFR은 비공개 `.tools/load-profile-104a6e09ad0343a884f7dbb6793011d5/`
안에0600으로 보관하고 공개할 수 있는 호출 stack 집계만 별도 `summary.json`으로 분리했다.
JFR를 켠 진단의 p95는56.16ms이며 위 성능 기준선에 혼합하지 않는다.

성능 예산은 UNSET이며 기본 명령의 전체 규모 측정만으로 M8을 완료 처리하지 않는다.
인증 의미를 보존하는 병목 개선과 같은 조건의 재측정은 [후속 근거](m8-authentication-load.md)를
따른다. 합의한 지연/오류/지속 시간 기준은 남는다.
MQTT payload·모델 계산·Dashboard·실제 센서/장비·장시간·클러스터 확장 성능은 이 시험 범위 밖이다.
M5/M7의 남은 외부 계약 수용과 M9/M10도 유지한다.
