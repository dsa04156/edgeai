# 감사 저장 부하의 추가 진단

2026-10-04. [ADR0067](../adr/0067-management-audit-group-commit.md)의 미채택 결정을 유지한다.
아래는 공유 호스트의 디스크 지연과 별도 작업 복사본의20ms 동시 커밋 비교다. 제품 API는
개별 transaction을 유지하며 JAR SHA256은 `3968964d694d6291cc69fb60ce545d540b0d0d379f6ae108f65439554f7174b7`이다.
V34와 감사의 영속 접수·실패 경계·대기열/부하 기본값은 바꾸지 않았다. M8 성능 합격 기준은 미정이다.

## 같은 파일시스템의 동기화 관측

PostgreSQL WAL과 같은 ext4 장치에 만든 시험 전용8MiB 파일에서8KiB pwrite/fdatasync를
60초 측정했다. 늦어진 예정 슬롯은 밀어 넣지 않고 별도로 셌다. 원래 DB 파일·설정·공유
서비스를 변경하지 않았으며 마지막 기록값을 읽고 파일 신원을 확인한 뒤 시험 파일만 삭제했다.

| 예정 빈도 | 완료 / 놓친 슬롯 | p95 / 최대 동기화 지연 | 실행 근거 |
|---|---|---|---|
| 초당100회 | 5,992 / 8 | 6.915 / 47.090ms | `20261004T060245Z-e48f83f1` |
| 초당300회 | 13,970 / 4,030 | 6.867 / 524.936ms | `20261004T060611Z-df716358` |

DB를 거치지 않아도 같은 장치에서 긴 동기화 지연이 발생할 수 있음을 관측했다.
단일 파일의 동기화 횟수는 PostgreSQL transaction 처리량과 같지 않으며, 이 결과만으로
저장장치 고장이나 기존 API 실패의 원인을 확정하지 않는다. 공유 호스트의 다른 I/O도 존재한다.

## 20ms 비교

별도 작업 복사본에서 이전2ms 프로토타입의 수집 대기만20ms로 바꿨다. 비교 JAR은
`d0e0bd7d2067733f6ece0602a257e8cdf882c8da1f9af31bdc94a90f11131b7f`다. 최대64개 묶음,
512개 감사 대기열, 실제 commit 이후 응답, API512MiB/Hikari5와 부하32worker/64pending을 유지했다.
이 실험은 main에 적용하지 않았다.

기본100→300→1,000대/각60초 `20261004T060930Z-5109f3bf`는9,240건/오류·미발송0,
최종 감사12,105쌍·고유 감사 transaction7,459개와 소유 API/DB 정리를 확인했다.
예정 시각 p95는64.08/53.87/54.02ms다. 그러나100대 구간의 최대 요청 지연은2,707.52ms,
p99는2,135.78ms였다. 평균이나 p95만으로 긴 지연의 해결을 주장하지 않는다.

1,000대/110RPS·180초의 JFR/PG 진단 `20261004T061538Z-de100f77`은 FAIL이다.
19,800건 예정 중19,792건이 성공하고8건이 미발송됐으며 예정 시각 p95는54.93ms였다.
소유 API/DB는 정리했다. 기존 driver는 미발송 판정에서 종료해 마지막 DB/감사 정합성 검사를
실행하지 않았으므로 이 실행의 최종 정합성은 확인하지 못했다.

8건은175.84–175.95초에 집중됐다.175.48/175.74초의 PG 표본에서 한 연결은 WALSync,
나머지 네 연결은 idle이었다. 다만 JFR를175초만 기록하도록 설정하여 이 구간의 JVM 기록은
없다.10,633,050bytes의 기록 파일을 같은 장치에 저장하는 시점도 가까우므로 계측 영향이
가능하다. 기록 내 최대 JDBC commit 대기92.31ms는24.27초로, 마지막 미발송을 설명하는
직접 증거가 아니다. 원시 JFR/PG 표본은 비공개이며 공개 근거에는 SQL/자격 증명을 넣지 않았다.

계측 영향을 구분하기 위한 비계측 비교 `20261004T062529Z-46ed9062`는 같은20ms JAR,
1,000대/110RPS·180초에서19,800건 전부 성공·오류/미발송0·예정 시각 p95 54.18ms였다.
최종 관측19,100행·감사21,505쌍/8,444transaction과 소유 API/DB 정리를 확인했다.
이 한 번의 성공은 진단 파일 저장이 앞선 실패의 유일한 원인이었다는 증거가 아니며,
공유 호스트 변동과100대에서 관측한 긴 지연은 여전히 남는다.

직후 기존 제품 JAR의 같은 비계측1,000대/110RPS·180초 비교
`20261004T063006Z-36e08240`는19,800건 중19,510건 전송 성공/290건 미발송으로 FAIL이다.
미발송은50–55초 구간에 몰렸고 예정 시각 p95는17.53ms, 최대 dispatch 지연은2,920.26ms다.
아래 보고서 보완으로 실패 구간의 장치/세션 각1,000개·관측18,736행·감사20,741쌍/
41,479transaction을 확인했다. 관측 행 수는 초기1,000건과 성공 응답 관측17,736건의 합이다.
재접속 probe와 전체 정합성 검사는 실패 후 실행하지 않았고 소유 API/DB는 정리했다.

기존 방식이 p95는 더 낮지만 긴 정지 구간에서 요청을 놓쳤다.20ms 방식은 transaction 수를
줄이는 대신 평상시 대기 시간이 증가했다. 두 실행은 공유 호스트의 서로 다른 시점이며,
각각의 결과를 안정적인 개선 배수나 저장장치 원인 확정으로 해석하지 않는다.20ms 변형의
기능·실패 회귀와 더 강한 성능 근거를 확인하기 전에는 ADR0067의 제품 미채택 상태를 유지한다.

## 실패한 부하의 DB 관측값 보존

기존 driver에서 큐 포화가 발생하면 요청 수·지연만 남고 DB 관측값이 빠지는 문제를 재현했다.
실제 API 앞의 시험 클라이언트에300ms 지연과 worker1개를 적용했다. 수정 전
`20261004T062214Z-644cfc9a`는 기대한 부하 FAIL 뒤 `postWindowDatabase` 부재로 회귀 검사가 실패했다.

수정 후 `20261004T062331Z-f6a52a6a`는 실제 API/PG의 기존 네 가지 판정과 새 큐 포화 회귀를
모두 통과했다. 큐 포화 시험 자체는22건 예정 중8건 전송 성공/14건 미발송으로 FAIL을 유지했다.
전송된 관측7건을 포함한 DB 관측17행·장치/세션 각10개·감사42쌍/81transaction을 보존했으며,
전체 정합성 통과로 표시하지 않고 소유 API/DB를 정리했다. 보고서는
`20261004T062335Z-load-acceptance-315ba2dc`에 보관한다.

측정 구간 직후 한 SQL snapshot을 읽고, 실패 판정 전에 보고서에 저장한다. 결과 저장은 HTTP
응답 뒤에 끝날 수 있으므로 이 시점의 감사 접수/결과 차이를 유실로 단정하지 않는다.
정상 구간은 기존 재접속·재전송·정합성 검사를 그대로 수행한다. 새로운 관측과 회귀는
기본 부하량·성능 예산·실패 판정을 완화하지 않으며 GitHub Actions의 기존 부하 게이트에 포함한다.
