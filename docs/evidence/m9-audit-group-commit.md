# 관리 감사 동시 커밋 검증

2026-10-04. [ADR0067](../adr/0067-management-audit-group-commit.md)는 미채택 실험이다.
아래 시험은 영속 접수·실패 시 실행 차단·결과 미확정과 비밀값 배제를 유지하면서 동시 commit을
묶은 프로토타입의 기록이다. transaction 수 감소에도 요청 미발송이 재현되어 제품 서비스는
ADR0066의 개별 transaction으로 복원했다. 아래129/231개 시험 수는 최종 코드의 시험 수가 아니다.
검증 JAR SHA256은 `809940b6ba7b5126e8cbcb90636647fd83290be56e948870fcce9a9a846641bb`다.
V34를 포함한 적용 migration은 변경하지 않았다.

- 전체 PostgreSQL231개 `20261004T050403Z-3b3dee13` PASS. 새2개는32동시 접수/결과가

  실패하면 다섯 개 모두 rollback되는지 확인한다. 다음 묶음의 commit과 기존 접수 보존도 확인한다.
- 실제 패키징 API8개 `20261004T050553Z-e779f236` PASS. 실제 PostgreSQL의 접수 실패

첫 단위 `20261004T045542Z-83e37667`은129개 중11개 실패다. intrinsic monitor 대기의

첫 PostgreSQL `20261004T045949Z-00c717b3`은230성공/스트림1실패다. 새 감사5개는 통과했다.
기존 StreamRunIntegrationTest의 helper는 매번 새 worker를 만들어 첫64개만 조회했으며,
누적된 고정 시험 namespace의 active Run이121개였다. 이전 실행을 삭제하거나 worker의
제품 페이지 제한을 바꾸지 않고 매 JVM의 시험 namespace를 UUID로 분리했다. 같은 전체

## 부하 근거와 범위

선행 [감사 개별 커밋 측정](m9-management-audit.md)의 첫 전체 시험은1,000대에서108건
미발송, 예정 시각 기준 p95 351.90ms였다. 같은 설정 JFR 진단은 누락0/p95 228.13ms이나
계측 부하가 있어 직접적인 개선 배수의 기준으로 사용하지 않는다. JDBC socket 대기와 DB
WALSync/WALWrite를 관측했으며 BCrypt 표본 집중 시점과 지연 증가 구간은 일치하지 않았다.
이 근거가 첫 실행 실패의 모든 원인을 확정하지는 않는다.

새 전체 부하에서는 같은100→300→1,000대/각60초·11/33/110RPS·32요청 worker·Hikari5/
JVM512MiB를 유지한다. 공유 호스트/PG의 I/O 변동은 남는다. 전송 수·지연·DB와 감사 정합성 외에
새 DB의 감사 행 `xmin`을 대조한 고유 transaction 수를 보고한다. 이는 freeze 전의 새 시험 DB에
한정한 측정으로 운영 감사 식별자나 장기 transaction 이력이 아니다. fsync/synchronous_commit,
감사 저장 범위, offered load를 낮추지 않는다.

첫 동시 커밋 전체 측정 `20261004T050639Z-31efa1e8`은 FAIL이다. 100/300대는 미발송·HTTP
오류 없이 각각 감사955/3,505쌍을 보존했고 고유 감사 transaction은1,346/5,310개였다.
1,000대는6,600건 예정 중6,400건을 전송해 모두 성공했지만200건이 queue 포화로 미발송됐다.
예정 시각 기준 p95는23.98ms이며 최대 dispatch 지연은2,103.87ms였다. 낮은 p95만으로
개선을 수용하지 않는다. 실패 시점 이후의 마지막 DB/감사 정합성 검사는 실행되지 않았으며
소유 API/DB 정리는 완료됐다. 약47초의 긴 지연 원인은 추가 JVM/PG 동시 관측으로 확인한다.

같은 전체 조건의 JFR/PG 진단 `20261004T051739Z-eb12a207`은9,240요청·오류/누락0·
최종 감사12,105쌍·소유 API/DB 정리를 확인했다. 1,000대 예정 시각 p95는39.05ms이며
최종 고유 감사 transaction은15,876개다. JFR를 포함한 실행이므로 이전 비계측 실행과의
직접 성능 배수로 사용하지 않는다. 약54.16초의 감사 결과 commit에서 JDBC 응답462.13ms와
대기 호출자의 Condition 대기464.68ms가 겹쳤다. 같은54.33/54.59초 PG 표본은 한 연결의
WALSync와 나머지 네 연결의 idle을 보였다. 이 실행에서 GC pause 최대는5.59ms다.
따라서 이 구간은 감사 commit의 DB 응답 대기임을 확인했지만, 앞선200건 미발송 구간의
직접 JVM/PG 기록은 없으므로 그 실패의 원인 해결로 확대하지 않는다.

1,000대/110RPS를180초 유지한 추가 진단 `20261004T052236Z-4d15f1fa`는 FAIL이다.
기본100→300→1,000대 순서의 대체 시험이 아니며,19,800건 예정 중19,426건 전송 성공·
374건 미발송, 예정 시각 p95 278.59ms였다. 약114.54초의 감사 결과 commit에서 JDBC 대기
894.19ms를 관측했고, 같은114.69–115.25초의 PG 표본에서 WALWrite/WALSync 대기가
겹쳤다. 같은110–120초 구간에203건이 미발송됐다. GC pause 최대7.46ms였고, 이 진단의
PG checkpoint 완료 개수는 변하지 않았다. 원시 JFR/상세 PG 표본은 비공개로 보관하며 공개
보고서에는 SQL·credential 없이 지연/대기 종류·개수만 남긴다. 소유 API/DB는 정리했다.
부하 실패와 DB 커밋 대기가 같은 실행에서 재현됐으나 공유 저장장치의 근본 장애 원인이나
해결을 주장하지 않는다. 큐 확대·감사 비활성화·fsync 변경으로 실패를 숨기지 않는다.

실행·저장소47개 `20261004T052726Z-69649eee`는 공유 VD 복구의 MQTT 거절로1개 실패했다.
단독 재실행은 제품 변경 전에도 통과했다. 후속 [브로커 회수 재연결](m7-broker-first-reconnect.md)
재현/수정과 전체 회귀를 별도로 기록한다.

프로토타입과 MQTT 수정 조합의 전체47개는 `20261004T054527Z-cb63eb01`에서 PASS다.
프로토타입 백업13개 `20261004T054006Z-79bd276f`와 부하 판정4개
`20261004T054339Z-ee1df867`도 PASS다. 판정 시험은각60감사쌍·66–68transaction과 정리를
확인했다. 이 기능 회귀 성공이 위 부하 실패를 없애지는 않는다. 미채택 뒤 최종 코드의 검증은
[재연결 근거](m7-broker-first-reconnect.md)에 따로 기록한다.

실험을 제외한 최종 API JAR은 ADR0066의 검증본3968964d와 완전히 같고 writer 클래스가 없다.
이 JAR의 부하 판정4개 `20261004T055524Z-55dffcf0`도 PASS다. 새 감사 transaction 측정값은
각60접수/결과 쌍에117개였으며, 종료 코드·정합성·소유 자원 정리를 유지했다. 이 소규모 판정
회귀는 전체 규모의 기존 부하 실패나 합의 성능 수용 완료를 대체하지 않는다.

현재 외부 감사·보관 정책·사용자별 RBAC·종합 복구 및 합의 성능/실장비 수용은 미완료다.
