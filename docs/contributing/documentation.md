# 문서 작성 기준

문서는 처음 사용하는 사람이 목적과 조건을 이해하고 작업 결과를 확인할 수 있도록 작성합니다.
Kubernetes·Argo CD·KubeEdge 공식 문서의 소개, 개념, 작업 가이드, 운영·참고 자료 구성을 참고합니다.

## 문서 종류 선택

| 종류 | 답해야 할 질문 | 구성 |
|---|---|---|
| 시작하기 | 처음 어떻게 사용하나요? | 목표 → 준비 → 짧은 실습 → 확인 → 다음 단계 |
| 개념 | 무엇이며 어떻게 연결되나요? | 정의 → 관계 → 책임 → 다른 개념과의 차이 |
| 사용 가이드 | 특정 작업을 어떻게 하나요? | 목적 → 준비 → 순서 → 기대 결과 → 오류/정리 |
| 운영 절차 | 어느 환경에 어떤 영향을 주나요? | 적용 범위 → 대상·권한 → 실행 → 성공/실패 판단 |
| 참고 자료 | 정확한 필드·상태·기본값은 무엇인가요? | 계약·설정 원본 → 표 → 예외 |
| 기록 | 당시 무엇을 결정하거나 검증했나요? | 날짜·환경 → 근거 → 결과 → 한계 |

## 문체와 예제

- 제목 하나는 주제 하나를 설명합니다. 첫 문단에 독자의 목적을 씁니다.
- 사용자 안내는 `합니다` 문체를 쓰고, 구현 중 대화나 “이번 작업에서” 같은 시간 의존 표현을 넣지 않습니다.
- 명령 앞에 작업 디렉터리와 필요한 서비스를 설명합니다. 변경 명령은 대상과 영향을 밝힙니다.
- 실제 환경 주소를 보편적인 기본값처럼 쓰지 않습니다. 예제 자리표시자는 값을 바꿔야 함을 설명합니다.
- 예제의 출력은 기대 형식으로 표시하며 실행하지 않은 결과를 실제 성공 기록으로 쓰지 않습니다.
- 숫자·날짜·지원 상태는 원본을 확인합니다. API 개수를 여러 문서에 수기로 반복하지 않습니다.
- 제품 이름은 첫 사용에서 설명하고 이후 용어를 통일합니다. [용어집](../reference/glossary.md)을 기준으로 합니다.

## 정확성 확인

API는 OpenAPI와 controller, 환경변수는 `application.yml`·`.env.example`·실행 스크립트,
화면 동작은 실제 컴포넌트와 검증 결과를 대조합니다. 코드·기본 설정·현재 배포·과거 검증은 구분합니다.
ADR·evidence·history를 현재 동작처럼 다시 쓰지 않습니다. 잘못된 기록을 발견하면 정정 근거를 별도로 남깁니다.

## 웹 목록과 검증

주요 문서는 `dashboard/docs-navigation.json`에서 분야·읽는 순서·짧은 설명을 관리합니다.
일반 검색과 문서 목록은 사용자 문서를 우선하고 심화 구현·설계·시험 기록은 별도로 탐색합니다.
본문은 저장소 Markdown이 원본이며 웹용 복사본을 수작업으로 관리하지 않습니다.

OpenAPI 관리 경로가 바뀌면 API 참고의 자동 생성 목록을 갱신한 뒤 검사합니다.

```bash
node scripts/internal/check-docs.mjs --write-api-index
```

```bash
bash scripts/test/test-docs.sh
```

링크·목차·등록 순서·API 참고 동기화를 확인합니다. 문서 화면을 바꿨으면 Dashboard의
lint·build와 모바일/데스크톱 읽기 화면도 확인합니다.
