## 1 기술 개요와 개발 범위

본 기술은 불변 SERVICE 모듈을 DAG로 구성하고 Kubernetes 실행 자원에 배치하여 입력 파일, 작업 상태와 검증된 결과를 연결하는 실행 제어 기술이다. Run, Task, Attempt와 실제 Runtime을 구분하여 재요청, 재시도와 위치 전환을 추적한다. API 요청의 접수와 계산 결과의 성공을 별도로 판정한다. [1][2]

자체 개발 범위는 DAG 검증과 버전 관리, 실행 요청의 멱등성, 배치 및 Attempt 수명 관리, Runner claim과 신원 확인, 결과 객체의 내용 검증, 취소와 제한된 위치 전환이다. Kubernetes와 S3 호환 저장소, Python 실행 환경은 기반 소프트웨어로 사용한다. DDS의 이미지 빌드와 GitOps 배포 기능은 본 기술의 등록 범위에서 제외한다.

### 1 1 실행 객체

| 객체 | 역할 |
|---|---|
| ProfileVersion | SERVICE의 고정 버전, 입출력 및 실행 규격 |
| WorkflowVersion | 작업과 의존성을 발행한 불변 DAG |
| Run | 특정 버전과 입력으로 접수한 실행 |
| Task | DAG의 논리 작업 |
| Attempt | 재시도 또는 전환으로 구분되는 실행 시도 |
| Runtime 및 Result | 실제 실행 주체와 검증 후 확정한 결과 |

사용자가 편집 중인 그래프, 발행된 버전, 현재 실행의 입력은 서로 다른 수명으로 관리한다. 이미 실행 중인 Run을 새 편집 내용으로 조용히 변경하지 않는다.

## 2 실행 제어와 결과 확정 구조

### 2 1 작업 실행

DAG 발행 전에 순환, 없는 포트, 중복 입력과 지원하지 않는 연결을 검사한다. 실행 요청은 고정 버전과 매개변수, AUTO 또는 NODE 등의 지원 정책을 사용한다. 동일 요청 재전송에는 같은 Idempotency-Key를 사용하고 별도 실행에는 새 키를 사용한다. [1]

| 단계 | 처리 내용 | 확정 근거 |
|---|---|---|
| 접수 | 버전과 입력, 정책을 저장 | 동일 키와 요청 규격 일치 |
| 계획 | 의존성 및 자원 조건에 맞는 Attempt 구성 | 서버 영속 상태와 현재 노드 조건 |
| 배정 | 실제 Runtime 및 Pod 생성과 연결 | 계획 신원과 실제 Pod의 일치 |
| claim | Runner가 현재 Attempt 권한 확인 | Attempt, epoch, Pod-bound 신원 |
| 실행 | 입력 다운로드 후 자식 프로세스 실행 | 입력 파일 크기 및 digest 확인 |
| 결과 | 출력 업로드 및 commit 요청 | 현재 producer와 고정 객체 내용 검증 |

### 2 2 결과의 검증

Runner는 선언된 입력을 내려받아 SHA-256을 검사하고 shell을 통하지 않은 command와 args로 자식 프로세스를 실행한다. 출력은 일반 파일만 허용하고 심볼릭 링크와 누락 파일을 거절한다. 파일을 저장한 뒤 고정 object version, 크기와 digest를 사용하여 결과를 검증한다. S3 PUT이나 Pod 종료만으로 Task 성공을 판정하지 않는다. [2][3]

현재 Attempt가 아닌 producer의 늦은 commit은 현재 결과를 덮어쓰지 못한다. 작업 취소나 기한 만료 시 프로세스 그룹 종료와 자원 회수 상태를 함께 확인한다.

## 3 재시도와 실행 위치 전환

### 3 1 새 시도와 이전 시도 구분

재시도는 같은 Task에 새 Attempt를 만들고 이전 시도의 결과와 권한을 분리한다. 위치 전환도 같은 논리 Task를 유지하면서 새 Attempt와 epoch를 부여한다. 장애 retry 예산과 OFFLOAD 예산은 구분한다. 이전 producer 종료 및 권한 회수와 미완료 CREATE 정리 조건을 확인한 뒤 다음 시도를 만든다. [4][5]

| 상황 | 관리 원칙 |
|---|---|
| 응답 유실 | 동일 요청을 같은 멱등 키로 재전송 |
| 실행 실패 | 선언된 정책과 예산 안에서 재시도 |
| 명시적 노드 전환 | 현재와 다른 호환 노드 및 실행 조건 검사 |
| STREAM 그룹 전환 | 연결 그룹과 고정 checkpoint 등 해당 계약의 조건 검사 |
| 취소 및 기한 초과 | 새 실행과 직렬화하고 이전 권한 및 물리 실행 정리 |

자동 정책은 CPU, 메모리 또는 서비스 지연의 측정 조건과 연속 충족 횟수, cooldown과 최대 전환 횟수를 사용한다. 측정값이 없거나 오래되었을 때 조건을 충족했다고 추정하지 않는다. Operation의 SUCCEEDED는 새 실행의 기동 또는 전환 완료를 의미하며 최종 계산 Result의 성공과 별도이다.

### 3 2 지원 경계

RESTART와 선언된 일부 STREAM 전환 계약은 일반적인 임의 모델의 상태 복원 기능과 구분한다. 과거 VD supervisor 실행 정책은 종료되어 현재 연속 VD를 일반 Runner의 VD 실행 자원으로 배치하지 않는다. 외부 Remote의 실제 제공자 수용과 상태형 모델의 종합 checkpoint 복원은 잔여 범위이다. [6]

웹은 전환 대상, 상태와 실패 코드, 정책 판단 및 그룹별 고정 checkpoint와 시도 신원을 표시한다. 새 Attempt가 없는 종료 상태는 대기 중이라고 추정하지 않는다.

## 4 구현 및 시험 결과

### 4 1 확인된 동작

| 시험 구분 | 결과 | 범위 |
|---|---|---|
| 실제 NODE SERVICE | 입력 2와 3, 가중치 4와 5, bias 1의 계산 결과 24 | 2026년 10월 16일 실제 API 및 Runner 경로 [6] |
| 결과 내용 검증 | 고정 object version과 크기, SHA-256 및 공개 결과 대조 | 2026년 10월 14일 실시간 입력 Run의 결과 파일 [6] |
| Runner 구성 요소 | 정상 실행, 손상 입력, 누락 및 링크 출력, timeout, 취소, commit 재전송 | 별도 HTTP fixture 시험 [2] |
| 실행 전환 | 명시적 NODE 전환과 상태 및 권한 정리, 관련 STREAM 그룹 인계 | 해당 ADR과 이전 검증 조건에 한정 [4][5] |
| native 전환 이력 | 대상과 정책, 실패 시도 부재, checkpoint, 상태 자동 반영 | 2026년 10월 20일 브라우저 HTTP fixture [6] |

2026년 10월 20일 실제 API 읽기 점검에서는 기존 Run 6개와 Task 12개를 조회하여 저장된 STREAM 경로 6개를 확인하였다. 조회한 Task의 전환 이력은 0건이었으므로 해당 화면의 전환 생명주기는 fixture로 검증하였다. UI 회귀의 성공을 새로운 실제 노드 전환 시험으로 표현하지 않는다. [6]

### 4 2 재현 및 인수

Runner 시험은 `scripts/test/test-runner.sh`를 사용하고 실제 PostgreSQL, broker 및 Kubernetes 시험은 준비 조건을 갖춘 별도 경로로 실행한다. 시험 시 같은 요청 재전송, 잘못된 신원, 이전 epoch commit과 취소 후 결과 거절을 포함한다. 실제 Result 검증에서는 API 상태와 객체 byte를 함께 확인한다.

## 5 개발 기여와 인수 조건

### 5 1 자체 개발 산출물

DAG와 실행 객체의 트랜잭션 경계, 요청 멱등 처리, producer 신원과 결과 검증, 재시도 및 전환 Operation, Python Runner와 관리 화면 연동이 개발 산출물이다. 주요 소스는 `backend/domain`, `backend/app`, `backend/adapters`, `runner/` 및 `dashboard/kestra-native/`에 있다. 인터페이스는 공개 관리 API와 내부 Runner API를 구분한다.

Kubernetes는 실제 Pod 실행 및 노드 배정을 제공하고 S3 호환 저장소는 고정 객체 버전을 제공한다. 이들 기반 제품과 Kestra UI의 기존 기능은 원본과 라이선스를 유지한다. 본 기술은 Kestra 서버의 워크플로 실행 엔진을 개발하거나 도입한 것으로 기술하지 않는다.

### 5 2 한계와 후속 수용

실제 GPU 및 NPU 모델 실행, 외부 Remote 제공자 전체 계약, 모든 상태형 서비스의 checkpoint 복원, 24시간 부하와 종합 복구는 별도 수용이 필요하다. 장비 사용률이 보인다는 이유로 해당 장비에서 모델이 성공적으로 실행되었다고 판정하지 않는다. [6][7]

인수자는 배포할 Runner 이미지 digest, 허용된 실행 규격, 대상 노드 아키텍처, 내부 TLS와 Pod 신원, 결과 저장소 versioning 및 읽기 권한을 확인한다. 기존 Flyway migration을 임의로 수정하지 않고 기준 소스의 설치 및 업그레이드 절차를 따른다. 세부 인수 구성과 시험표는 TDP-02에 수록한다.
