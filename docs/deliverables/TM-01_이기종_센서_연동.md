## 1 기술 개요와 개발 범위

본 기술은 서로 다른 통신 방식의 센서를 KubeEdge 장치 모델에 연결하고, 측정 항목의 설정과 실제 수집 상태를 웹에서 관리하는 연동 기술이다. 물리 보드와 측정 항목을 구분하여 여러 항목이 같은 연결과 Mapper를 공유하도록 구성하였다. 장치 등록, 연결 시험, 항목 추가와 수정, 최신 관측 및 원본 이력 조회를 하나의 관리 흐름으로 연결하였다. [1][2]

개발 범위는 프로토콜별 입력 검증, DeviceModel과 Device CRD 구성, 노드별 공유 Mapper 조정, DMI 상태 보고와 MQTT 데이터 경로 연계, 관리 API 및 웹 양식이다. KubeEdge 자체와 통신 라이브러리는 기반 소프트웨어로 사용하였다. 센서를 등록했다는 사실과 실제 연결에 성공했다는 사실을 별도 상태로 관리한다.

### 1 1 적용 대상

| 항목 | 적용 범위 |
|---|---|
| 입력 연결 | Modbus TCP, OPC-UA, MQTT 입력, HTTP JSON Virtual, Serial JSON, Sense HAT v1, RTSP |
| 관리 단위 | 센서 측정 항목별 Device와 Property 설정 |
| 실행 단위 | 대상 노드와 프로토콜별 공유 Mapper |
| 상태 원본 | KubeEdge Device 및 DeviceStatus, DMI heartbeat, 실제 수집 시각 |
| 데이터 경로 | 최신 상태 보고와 별도 MQTT 관측 전달 |

Arduino의 raw 값은 환산 전 숫자로 관리하며 온도나 가속도의 물리 단위를 임의로 부여하지 않는다. Sense HAT은 ARM64 Raspberry Pi의 v1 보드를 지원 대상으로 한다. RTSP는 실제 프레임 디코딩 여부를 확인하는 별도 드라이버를 사용한다.

## 2 구성 요소와 수집 절차

### 2 1 관리 경로와 데이터 경로

관리 API는 사용자가 지정한 프로토콜, 대상 노드, 연결 정보와 측정 항목을 검증한 뒤 KubeEdge 리소스에 반영한다. 인터페이스가 같은 항목은 DeviceModel을 재사용하고, 같은 노드와 프로토콜의 장치는 공유 Mapper 설정에 추가한다. 기존 장치의 항목을 수정할 때 다른 연결 설정이나 항목을 덮어쓰지 않는다. [1][2]

데이터는 두 경로로 나뉜다. DMI를 통한 DeviceStatus와 Twin 보고는 최신 상태를 관리한다. 매 수집 관측은 별도 MQTT 경로로 전달하여 원본 저장과 연속 계산에서 사용한다. Twin 값이 같아 갱신되지 않는 경우가 있으므로 수집 지속 여부는 heartbeat와 실제 MQTT 수신도 함께 확인한다.

| 순서 | 수행 주체 | 처리 내용 |
|---|---|---|
| 1 | 관리 API | 필수 필드, 자료형, 포트, 수집 간격과 항목 매핑 검증 |
| 2 | 장치 관리자 | DeviceModel 재사용 또는 생성, Device CRD 반영 |
| 3 | 공유 Mapper | 연결 구성 로딩, 프로토콜 드라이버로 값 읽기 |
| 4 | DMI 경로 | 상태와 최신 측정 항목 보고 |
| 5 | MQTT 경로 | 관측 신원을 포함한 원본 발행 |
| 6 | 관리 화면 | 등록 결과, 연결 상태, 측정 시각과 값을 표시 |

### 2 2 관측 신원

검증 관측은 원본 UID, property, 수집 설정 식별자, source generation, session, sequence와 측정 시각을 유지한다. 같은 이름으로 재등록한 장치의 이력은 UID로 구분한다. 구형 DataModel 형식은 설정 미검증으로 표시하고 검증 관측과 동일한 권한을 부여하지 않는다. [3]

세션 순번은 Mapper가 영속 보관한다. 저장 실패 시 기존 상태 보고와 원본 경로를 보존하면서 검증 관측 발행을 대기한다. 노드 저장소를 잃은 경우에는 source generation의 명시적 변경이 필요하다.

## 3 프로토콜 설정과 관리 인터페이스

### 3 1 연결 정보 검증

| 프로토콜 | 주요 입력 | 현재 제약 |
|---|---|---|
| Modbus TCP | Host, Port, Unit ID, register, 함수, 바이트 순서 | 표기 register와 wire address를 구분 |
| OPC-UA | endpoint path, NodeId, 자료형 | Anonymous 및 SecurityMode None |
| MQTT 입력 | broker, 정확한 topic, JSON 경로 | wildcard와 자체 출력 topic 사용 제한 |
| HTTP Virtual | HTTP endpoint, JSON 경로 | 임의 장치 자동 발견 기능 없음 |
| Serial JSON | 장치 경로, baud rate, 프레임 sensor | 지정한 노드의 장치 경로가 필요 |
| Sense HAT v1 | source Device ID, I2C 장치 경로 | 지원 보드와 아키텍처 확인 필요 |
| RTSP | host, port, path, timeout | 인증 없는 RTSP 및 TCP 전송 |

Modbus holding 40001과 input 30001은 각각 해당 함수의 wire address 0에 대응한다. JSON 경로는 객체 키를 점으로 연결하는 형식을 사용한다. RTSP 연결 시험은 TCP나 SDP 응답만으로 성공시키지 않고 영상 프레임을 디코딩해야 성공한다. [1]

### 3 2 항목 단위 변경

항목 추가는 기존 연결을 재사용하면서 중복 항목을 거절한다. 수정은 선택한 항목의 자료형, 값 위치, 단위, 배율과 보정값에 한정한다. 항목 이름은 워크플로 참조를 유지하기 위해 고정한다. 동시 변경은 서버의 최신 설정과 resourceVersion을 기준으로 검사한다.

센서 관리 프록시는 `/api/devices`와 `/api/device-profiles` 계열을 사용한다. 서버의 관리용 계약과 일반 실행 장치의 UUID API를 혼동하지 않도록 TDP-01의 인터페이스 목록과 구현 컨트롤러를 함께 확인한다. 쓰기 요청은 기존 CSRF 세션을 사용한다. [1][4]

마지막 항목 삭제는 해당 센서의 등록 리소스도 제거한다. 같은 물리 연결의 다른 센서와 공유 Mapper, 저장 규격과 기존 이력은 보존 범위를 구분하여 처리한다.

## 4 구현 및 시험 결과

### 4 1 구현 산출물

Go Mapper의 프로토콜 드라이버와 DMI 클라이언트, Spring 장치 관리 서비스, KubeEdge 배포 규격과 Vue 센서 등록 양식이 주요 산출물이다. Mapper 실행과 관측 규격은 `mappers/`와 `deploy/kubeedge/`에, 관리 화면은 `dashboard/kestra-native/`에 포함된다. 원본 수집 저장 기술은 TM-03에서 별도로 설명한다.

### 4 2 확인한 시험과 해석

| 검증 구분 | 확인 내용 | 근거와 해석 |
|---|---|---|
| 실제 센서 연결 기록 | Arduino Serial JSON과 Sense HAT 측정 항목 연결 및 값 관측 | 기존 장치 등록 가이드의 물리 연결 기록 [1] |
| 항목 관리 | 단일 항목 수정, 연결 공유, 다른 항목 보존, 충돌 및 오류 처리 | 관리 API와 웹 회귀 검증 기록 [4] |
| 원본 신원 | 설정 미검증 원본 구분, UID와 세션을 유지한 조회 | 연속 처리 및 저장 계약 [3] |
| native API 경계 | 등록 요청, 단일 항목 수정, 실패와 CSRF 경계 | 2026년 10월 20일 기존 콘솔 시험 27개 전체 통과 중 관련 사례 [4] |
| RTSP | 프레임 기반 연결 판정과 JPEG 조회 경로 | 데모 스트림 검증이며 특정 실물 카메라 호환 수용과 구분 [4] |

2026년 10월 20일 기록에서는 Jetson 및 Arduino와 합성 RTSP 데모의 연결 복구를 보류하였다. 이 보류 상태는 과거 실제 센서 연결 시험과 별도로 관리한다. RTSP 데모는 실물 카메라의 호환성을 확인한 결과로 사용하지 않는다. [4]

신규 설치 인수 시험은 연결 성공, 실제 시각의 전진, 값의 자료형과 단위, 재등록 UID 분리, 실패 시 마지막 상태 표시를 다시 확인해야 한다. 프로토콜 목록에 있다는 사실만으로 모든 제조사 장치와 보드의 호환성을 판정하지 않는다.

## 5 개발 기여와 적용 조건

### 5 1 자체 개발과 기반 소프트웨어

자체 개발 범위는 이기종 연결 규격을 공통 관리 흐름으로 변환하는 어댑터, 측정 항목별 CRD 구성, 공유 Mapper의 설정 수명 관리, 관측 신원 부여, 관리 API와 웹 연동이다. KubeEdge의 CRD 및 DMI 체계, Go 통신 라이브러리와 MQTT 브로커는 기반 기술이다. 제출 시 원본 라이선스와 제3자 고지를 함께 보존한다.

KubeEdge 장치 신원과 일반 워크플로 실행용 UUID DeviceSession은 별도 모델이다. Mapper 센서 등록을 일반 STREAM 경로의 자동 생성으로 해석하지 않는다. 장치 명령 쓰기, 임의 장치 자동 발견, 모든 프로토콜의 인증 및 TLS 확장은 본 문서의 완료 범위에 포함하지 않는다.

### 5 2 인수 및 후속 검증

인수자는 대상 Edge Node의 Ready 상태와 DMI 지원, 아키텍처별 Mapper 이미지, 실제 장치 경로와 네트워크 도달성을 확인한다. 저장한 항목 규격이 보드 출력과 일치하는지 대조한 뒤 연결 시험과 실제 관측을 확인한다. 복구 중에는 등록 목록만을 근거로 ONLINE을 만들지 않는다.

실센서 장기 손실률과 저장소 중단 후 전체 복구, 새로운 장치의 호환성은 별도 시험 대상이다. 본 문서의 시험 결과는 각 기록의 날짜와 조건에 한정한다. 배포 및 인수 절차와 파일 구성은 TDP-01을 참조한다.
