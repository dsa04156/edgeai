## 1 기술 개요와 개발 범위

본 기술은 물리 센서의 검증 원본 또는 연속 가상디바이스의 현재 유효 계산 결과를 일반 SERVICE 워크플로의 입력으로 사용하는 연계 기술이다. 사용자가 입력 종류와 데이터를 바꾸어도 후속 처리 작업과 연결을 보존하고 새 DAG 버전 및 새 Run에 반영한다. 같은 실행 안에서는 최신 유효값을 반복 조회하여 처리 작업으로 전달한다. [1]

자체 개발 범위는 원본 catalog, typed data source 설정, Run별 원본 신원 고정, 권한을 제한한 입력 reader, 중복 표본 제거, EXTERNAL journal 연계와 정상 입력 종료, 편집기의 원본 선택 양식이다. 센서 원본 MQTT와 Task STREAM을 직접 같은 topic으로 간주하지 않고 서로 다른 신원과 처리 계약을 연결한다. [2]

### 1 1 입력 모드

| 입력 종류 | 읽는 값 | 원본 변경 시 의미 |
|---|---|---|
| 센서 | NanoMQ 수집 경로에서 저장한 검증 원본의 최신 유효값 | UID, 설정 또는 source generation 변경 시 기존 Run 차단 |
| 가상디바이스 | eKuiper의 current VALID 출력 | revision 또는 실행 generation 변경 시 기존 Run 차단 |
| 기존 BATCH 장치 입력 | Run 접수 시 고정한 최신 측정 | 접수 후 연속 갱신하지 않음 |

현재 실시간 입력은 최신값을 1초마다 읽는 방식이다. 모든 중간 관측의 전량 전달, 구독 재생 및 과거 전체 데이터 재처리는 본 기술의 보장 범위가 아니다.

## 2 원본 선택과 실행 신원 고정

### 2 1 편집 및 발행

WORKFLOW_DATA 입력 모듈은 입력 종류와 입력 데이터를 선택하는 양식을 제공한다. 선택 변경은 해당 작업의 dataSource 설정만 바꾸고 노드 ID, 다른 매개변수, 후속 작업과 연결, 캔버스 위치를 유지한다. 기존 실행의 원본을 즉시 교체하지 않고 새 불변 버전을 발행하여 적용한다. [1]

원본 목록은 조회 중, 빈 목록, 실패와 재조회 상태를 구분한다. 목록에서 사라진 기존 선택을 다른 원본으로 자동 대체하지 않는다. 가상디바이스는 먼저 시작하여 유효 결과가 있어야 하며 저장 정책이 NONE이어도 current VALID 출력을 입력으로 사용할 수 있다.

### 2 2 데이터 경계

| 단계 | 고정 또는 검사 항목 | 목적 |
|---|---|---|
| 발행 | 원본 종류와 대상, property 또는 output | 사용자 입력 의도 보존 |
| Run 생성 | 원본 UID, 설정 또는 revision, 실행 세대 | 다른 원본으로의 묵시적 교체 방지 |
| reader 접근 | 현재 Attempt와 Pod 범위의 권한 | 임의 작업의 원본 접근 제한 |
| 표본 읽기 | 신선도와 sampleId | 만료값 배제 및 중복 전달 방지 |
| journal commit | cursor, 상태와 emission | 확인 위치와 전달 상태의 일치 |

아직 값이 없거나 만료된 경우 유효값을 기다린다. 원본 신원이 바뀌면 기존 Run을 차단하고 새 버전 및 실행을 명시적으로 요청하게 한다. CRD 센서 이름을 일반 DeviceSession의 UUID로 바꾸어 권한을 우회하지 않는다.

## 3 전달과 정상 종료 계약

### 3 1 표본과 journal

입력 SERVICE는 유효한 새 sampleId를 읽고 source cursor와 emission을 같은 EXTERNAL journal commit에 확정한다. 기존 STREAM의 DATA, ACK와 외부 checkpoint 계약을 재사용하여 단순 조회 위치와 처리 확정 위치를 구분한다. 저장소 업로드 성공만으로 소비자의 처리 확인 위치를 전진시키지 않는다. [1][3]

센서 수집 MQTT의 PUBACK은 원본 저장 승인이고 Task STREAM의 ACK는 해당 처리 계약의 확인이다. 두 승인을 합쳐서 센서의 모든 관측이 처리되었다고 해석하지 않는다. 1초 조회 사이의 중간 관측은 선택되지 않을 수 있다.

### 3 2 정상 종료

| 순서 | 수행 내용 |
|---|---|
| 1 | 새 입력 읽기를 끝내는 drain 요청 |
| 2 | 마지막 DATA와 END를 journal 규칙에 따라 전달 |
| 3 | 처리 ACK와 서버 확정 checkpoint 확인 |
| 4 | 연결 그룹의 공동 FINALIZE 대기 |
| 5 | 최종 결과 파일 저장과 검증된 Result 확인 |

정상 종료는 작업을 강제 취소하는 기능과 구분한다. 예제 처리기는 수신 표본 수와 마지막 값, 숫자 통계를 파일로 남긴다. SERVICE의 시간 한도는 최대 24시간이므로 이 기능을 무기한 상시 처리 서비스로 기술하지 않는다. [1]

저장소 또는 권한 실패, 원본 세대 변경과 늦은 종료 응답은 해당 오류와 실행 상태로 표시한다. 사용자가 정상 종료를 눌렀다는 사실만으로 Run 성공을 만들지 않는다.

## 4 실제 실행 및 회귀 시험

### 4 1 실측 연계 기록

| 날짜 및 대상 | 결과 | 확인 기준 |
|---|---|---|
| 2026년 10월 14일 센서 입력 예제 | Arduino 가속도 원본 39건을 동일 처리기에 전달 | source와 처리 건수, 마지막 값 및 END 일치 |
| 같은 날 가상디바이스 입력 예제 | eKuiper 온도 계산 85건 전달 | 각 2개 Task의 Run이 SUCCEEDED, 결과 VALID |
| 같은 날 파일 검증 | 고정 object version 4개의 크기와 SHA-256 대조 | 독립 TLS 조회 및 공개 결과 내용 확인 |
| 2026년 10월 16일 후속 연계 | 센서 60건 및 VD 8건의 연속 전달과 정상 종료 | 실제 API 및 Runner, 마지막 센서 Run의 source와 처리 60건 일치 |

위 결과는 선택된 최신 표본의 전달과 종료를 확인한 것이다. 물리 센서가 발행한 전체 관측의 전량 수신율을 측정한 결과로 확대하지 않는다. 날짜별 실행과 파일 개수는 별도 시험이며 하나의 Run 결과로 합치지 않는다. [4]

### 4 2 회귀 검증

공개 Run API와 PostgreSQL 시험에서는 typed pin, 같은 요청 재전송, reader 권한 범위, 만료 및 원본 generation 변경을 검사하였다. Runner 및 SDK 시험에서는 완료 응답 유실, 취소, 기한과 복구 조건을 다루었다. 웹에서는 입력만 바꿔 새 버전을 발행하면서 후속 작업과 연결을 보존하는 동작을 확인하였다. [4]

인수 환경은 예제 이미지의 0 digest를 실제 준비한 immutable 이미지로 바꾸어야 한다. 예제 설정 파일이 존재한다는 사실을 실제 배포 완료로 취급하지 않는다. 사용한 Runner 이미지의 아키텍처와 시험 경로를 함께 기록한다.

## 5 개발 기여와 적용 조건

### 5 1 기여 범위

센서 및 VD 원본 모델을 일반 워크플로 입력 계약으로 연결하는 계층, 원본 신원 pin과 reader 권한, cursor와 emission의 journal 연계, 정상 종료 및 결과 검증 연결, 편집기 입력 선택 보존이 자체 개발 범위이다. 원본 수집기는 TM-03, eKuiper 계산은 TM-02, 일반 Runner 결과 관리는 TM-04와 연계된다.

주요 소스는 WorkflowDataInputService, WorkflowDataSourceController, WORKFLOW_DATA 및 sample 예제 프로필과 Runner의 관련 STREAM 모듈이다. 소프트웨어 설치와 인수 자료는 TDP-02에 포함하며 TDP-01의 센서 및 VD 준비 조건을 전제로 한다.

### 5 2 한계와 후속 시험

전량 관측 feed, 일반 Mapper MQTT의 무조건 자동 STREAM binding, 모든 상태형 모델의 복원, 외부 Remote 제공자의 실제 처리 수용은 남아 있다. 현재 latest-value polling과 journal을 조합한 기능만을 근거로 이들 범위를 완료로 판정하지 않는다. [5]

실행 예제는 당시 확인한 amd64 개발 Runner 기준이다. ARM64 공식 실행 수용, 실제 AI 모델과 GPU 및 NPU 추론 성능, 장기 동작은 별도 확인이 필요하다. 2026년 10월 20일 Arduino 연결 복구 보류 상태에서는 실제 센서 연계 시험을 새로 성공한 것으로 표시하지 않는다.
